# Base64 / Base32 인코딩 정리

## 1. Base64란?
- 이진 데이터를 **텍스트 문자 64개**(`A-Z`, `a-z`, `0-9`, `+`, `/`)로 표현하는 **표기 방식**
- 암호화도, 압축도 아님 (누구나 쉽게 디코딩 가능)

## 2. 왜 쓰는가?
- 이메일(SMTP), JSON, XML, HTML, URL 등 **텍스트 전용 통로**에서는 이진 데이터의 줄바꿈, 제어 문자, 널 문자 등이 깨지거나 특별하게 해석될 수 있음
- 안전한 문자만 쓰면 어떤 시스템을 거쳐도 데이터가 변형되지 않음
- 활용 예: VLM API 이미지 전송, `data:image/png;base64,...`, 이메일 첨부(MIME), JWT, Basic Auth

## 3. 동작 원리 (`Man` → `TWFu`)
1. 글자를 ASCII 8비트로 변환: `01001101 01100001 01101110`
2. 24비트를 이어 붙임
3. 6비트씩 4덩어리로 나눔: `010011 | 010110 | 000101 | 101110`
4. 10진수로 변환: 19, 22, 5, 46
5. Base64 표에서 문자 찾기: `T`, `W`, `F`, `u`

| 숫자 범위 | 문자 |
|---|---|
| 0~25 | A~Z |
| 26~51 | a~z |
| 52~61 | 0~9 |
| 62 | + |
| 63 | / |

## 4. 패딩(`=`)
- Base64는 **4글자 단위**로 출력하도록 약속되어 있음
- 마지막 묶음이 모자라면 비트는 `0`으로 채우고, 글자 자리는 `=`로 채움

| 남는 바이트 | 실제 글자 | 패딩 | 예시 |
|---|---|---|---|
| 3 | 4 | 없음 | `Man` → `TWFu` |
| 2 | 3 | `=` 1개 | `Ma` → `TWE=` |
| 1 | 2 | `=` 2개 | `M` → `TQ==` |

- `=`의 역할: 원본이 몇 바이트였는지 알려 주는 **길이 정보**, 그리고 4글자 경계 유지
- `0` 대신 `=`를 쓰는 이유: `0`은 이미 Base64 문자(52번)라 실제 데이터와 구분 불가
- `=`로 정한 것은 필연이 아니라 **표준(RFC 4648)의 합의된 규칙**

## 5. 용량이 늘어나는 이유
- 문자 종류가 적을수록 글자 1개에 담기는 정보(비트)가 줄어듦
- 그런데 글자 1개는 저장 시 항상 1바이트(8비트)를 차지함
- Base64: 3바이트 → 4바이트, **약 33% 증가**
- 이는 비효율이 아니라 **안전한 통로를 쓰기 위한 비용**

| 방식 | 문자 수 | 글자당 비트 | 증가율 |
|---|---|---|---|
| 원본 | 256 | 8 | 0% |
| Base85 | 85 | 약 6.4 | 약 25% |
| Base64 | 64 | 6 | 약 33% |
| Base32 | 32 | 5 | 약 60% |
| Hex (Base16) | 16 | 4 | 100% |

`Man` 비교: Hex `4D616E`(6글자) / Base64 `TWFu`(4글자)

## 6. Base32 패딩 규칙
- 기준: **5바이트(40비트) → 8글자** (5비트 × 8 = 8비트 × 5)
- 5바이트가 안 되면 `=`로 **항상 8글자**를 맞춤
- 실제 글자 수 = (입력 비트 수 ÷ 5) 올림, `=` 개수 = 8 − 실제 글자 수

| 입력 바이트 | 비트 | 실제 글자 | `=` 개수 |
|---|---|---|---|
| 1 | 8 | 2 | 6 |
| 2 | 16 | 4 | 4 |
| 3 | 24 | 5 | 3 |
| 4 | 32 | 7 | 1 |
| 5 | 40 | 8 | 0 |

### 예시: `M` → `JU======`
- `01001101` → `01001 | 101` (뒤 덩어리는 3비트뿐)
- 뒤에 `0` 2개를 붙여 `10100`으로 만듦
- 9 → `J`, 20 → `U`, 나머지 6자리는 `=`

### 디코딩: `JU======` → `M`
1. `=` 제거 → `JU`
2. 숫자로 변환 → 9, 20
3. 5비트로 변환 → `01001`, `10100`
4. 이어 붙임 → `0100110100` (10비트)
5. 8비트씩 끊기 → `01001101` | `00` (남은 `00`은 채움값이므로 버림)
6. `01001101` = 77 = `M`

## 7. 입력 단위와 처리 단위
- **입력**은 항상 바이트(8비트) 단위
- **글자 1개를 만드는 단위**(4~6비트)는 이미 8비트보다 작음
- **묶음 단위**는 "글자 비트 수와 8의 최소공배수"로 정함

| 방식 | 글자당 비트 | 최소 묶음 |
|---|---|---|
| Base64 | 6 | 24비트 (3바이트 → 4글자) |
| Base32 | 5 | 40비트 (5바이트 → 8글자) |
| Hex | 4 | 8비트 (1바이트 → 2글자) |

- 더 큰 묶음(예: 6바이트)도 가능하지만 결과가 같아서 이점이 없음
- 묶음을 1바이트로 줄이면 매번 패딩이 생겨 비효율적
  - `Man` 3바이트 묶음: `TWFu` (4글자)
  - `Man` 1바이트씩: `TQ==YQ==bg==` (12글자, 3배)

## 8. 핵심 암기
> **Base64 = 텍스트 전용 통로를 통과해야 할 때 쓰는 이진 → 텍스트 변환 방식**
> 3바이트 → 4글자 / 용량 약 33% 증가 / 암호화 아님

```python
import base64
base64.b64encode(b"Man")   # b'TWFu'
base64.b64decode("TWFu")   # b'Man'
base64.b32encode(b"M")     # b'JU======'
base64.b32decode("JU======")  # b'M'
```
